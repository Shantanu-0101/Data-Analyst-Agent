# Data Analyst Agent — Implementation Plan

Based on `SPEC.md`. Builds the project in dependency order, so each phase can be run and checked before the next one starts. The layout is the spec's `data-analyst-agent/` tree, created in this folder.

---

## 0. Decisions to settle before coding

These are gaps or soft spots in the spec. Defaults are given so work isn't blocked; change any before Phase 3.

| # | Topic | Default chosen | Why |
|---|-------|----------------|-----|
| 1 | Gemini model name | `GEMINI_MODEL` in `config.py`, default `gemini-2.5-flash`, overridable from `.env` | Model names change and free-tier quotas differ per model; one place to change it. Verify the name against the current Gemini docs on day 1. |
| 2 | Sandbox strength | `exec()` with a **whitelisted `__builtins__`** and an **AST pre-check**, plus a timeout | The spec's `allowed_globals` alone does not restrict anything: `exec` injects full builtins (`open`, `__import__`) unless `__builtins__` is overridden. This is demo-grade protection against *accidental* damage, not a security boundary, and the README should say so. |
| 3 | Retry semantics | Initial run + up to **3 fix attempts** (4 executions max) | Spec routing is `retries < 3` with `fix` incrementing, which gives exactly this. |
| 4 | Free-tier rate limit | Worst case is 5 LLM calls per question (plan, generate, 3 fixes) against 15 RPM | Add a small retry/backoff on 429 errors and show a friendly "rate limited, retrying" message in the UI. Keep `plan` as its own node, as the spec says. |
| 5 | `result_type` for text vs number | `str` → `"text"` (`st.write`), `int/float/np.number` → `"value"` (`st.metric`) | The spec lists both but only defines "else → value". |
| 6 | "Chat history (clickable)" | Clicking a past question in the sidebar **re-asks it** | Spec doesn't say what a click does. Scroll-to is awkward in Streamlit. |
| 7 | Follow-up context | `history` stores `{question, code, result_summary}` for the last ~5 turns, injected into the plan and generate prompts | "Now filter that to 2024 only" needs the previous *code*, not just the question. |
| 8 | Python / packaging | Python 3.11+, venv, pinned versions in `requirements.txt` | Reproducible demo. |

## Phase 2 — Data layer (`src/data/loader.py`)

Functions:
- `load_csv(file_or_path) -> pd.DataFrame` — accepts a path or a Streamlit `UploadedFile`; tries UTF-8 then falls back to latin-1; parses columns named like dates (`date`, `*_date`) to `datetime64`; raises a readable error for empty or unparsable files.
- `extract_schema(df) -> dict` — columns with dtypes, row count, first 3 rows, null counts (only non-zero), `describe()` for numeric columns.
- `format_schema_info(df) -> str` — renders that dict into the **Schema Prompt** text from the spec (this becomes `state["schema_info"]`).
- `dataset_summary(df) -> dict` — rows, columns, total nulls, for the sidebar.

Guard against huge frames: truncate the `describe()` output and sample rows to a sane character cap so the prompt stays small.

**Check:** unit test that `format_schema_info` on `sales.csv` contains every column name and the correct row count.

## Phase 3 — Sandbox (`src/execution/sandbox.py`)

Build and test this before touching the LLM, since it is fully deterministic.

`run_code(code: str, df: pd.DataFrame) -> ExecResult` where `ExecResult = {result, result_type, error}`.

1. **Clean the code:** strip markdown fences (```` ```python ````) and leading prose, since models often wrap code despite instructions.
2. **AST pre-check:** reject `import`/`from … import`, names `open`, `eval`, `exec`, `compile`, `__import__`, `input`, `globals`, `locals`, `getattr`/`setattr` on dunder names, and any attribute starting with `__`. On rejection return an `error` string that explains the rule, so the fix node can act on it.
3. **Restricted environment:** `{"__builtins__": SAFE_BUILTINS, "pd": pd, "px": px, "np": np, "df": df.copy()}`. `SAFE_BUILTINS` is a whitelist: `len, range, sum, min, max, abs, round, sorted, enumerate, zip, list, dict, set, tuple, str, int, float, bool, isinstance, any, all, reversed, map, filter`. (`df.copy()` so a bad `inplace` edit cannot corrupt the user's data across questions.)
4. **Run with a timeout:** execute in a worker thread and `join(EXEC_TIMEOUT_S)`; on timeout return a timeout error (the thread can't be killed, so note this limitation in a comment).
5. **Capture** `RESULT` from the namespace; if missing, return an error "code did not set RESULT".
6. **Classify:** `DataFrame` → `dataframe`; `Series` → `.reset_index()` to a DataFrame; `plotly.graph_objs.Figure` → `plotly`; `str` → `text`; number → `value`; anything else → `str(...)` as `text`.
7. **Errors:** return `traceback.format_exc()`, trimmed to the last ~30 lines, to keep fix-prompts small.

**Check (pytest):** valid code returns each of the 4 result types; `import os` is rejected; `open("x")` is rejected; infinite loop times out; missing `RESULT` gives an error; a `KeyError` on a wrong column returns a traceback; two consecutive runs don't leak variables.

## Phase 4 — Prompts (`src/prompts/templates.py`)

Constants copied from the spec, as `str.format`-style templates:
- `SCHEMA_PROMPT` (system prefix, sent on every call)
- `PLAN_PROMPT` — question + schema + recent history; asks for 1–2 sentences
- `CODE_PROMPT` — the spec's rules, plus two additions: "if the question refers to a previous answer, build on the previous code shown below", and "prefer `px` charts with titled axes"
- `FIX_PROMPT` — traceback + original code, as in the spec
- `format_history(history) -> str` helper

Use `{{ }}` escaping where code fences or braces appear. Keep templates free of logic.

**Check:** each template formats without `KeyError` using dummy values.

## Phase 5 — Agent (`src/agent/`)

### `state.py`
`AgentState` TypedDict exactly as in the spec. Use `Optional[Any]` for `result` (the spec's `Optional[any]` is the builtin function, not a type).

### `nodes.py`
- `get_llm()` — `ChatGoogleGenerativeAI(model=GEMINI_MODEL, temperature=0)`, cached.
- `invoke_llm(messages)` — wraps the call with backoff on 429/quota errors (3 tries, exponential).
- `plan_node(state)` → `{plan}`
- `generate_node(state)` → `{generated_code}` (run through the sandbox's fence-stripper)
- `execute_node(state)` → calls `run_code`; returns `{result, result_type, error}` and clears `error` on success
- `fix_node(state)` → `{generated_code, retries: retries + 1}`

Nodes take the LLM through a parameter or module-level factory so tests can inject a fake.

### `graph.py`
`build_graph()` returns the compiled `StateGraph`: `plan → generate → execute → (should_retry) → fix → execute` or `END`. `should_retry` as in the spec (`error and retries < MAX_RETRIES` → `"fix"`, else `"end"`).

Also expose `ask(graph, df, schema_info, question, history) -> AgentState` as the single entry point used by the UI and the walkthroughs; it initializes `retries=0`, `error=None`, and appends the turn to `history` afterward.

**Check (pytest, no network):** with a scripted fake LLM — (a) good code on the first try ends with 0 retries; (b) bad code then good code ends with 1 retry; (c) always-bad code stops at `retries == 3` with `error` set. This verifies the loop and routing.

**Check (live, needs the key):** run all 8 sample questions from the spec against `sales.csv` and confirm each yields the expected output type. Record the results; they feed the report.

## Phase 6 — Streamlit app (`app.py`)

Layout per the spec's wireframe.

- **Sidebar:** `st.file_uploader` (CSV), a "Use sample data" button for the demo, dataset info (rows / columns / nulls), clickable chat history (buttons that set a `pending_question`).
- **Main:** dataset preview (`st.dataframe(df.head(10))`), "Schema & Stats" `st.expander`, then the chat.
- **Chat:** `st.chat_input` (it has its own send button, so no separate `[Send]`), and `st.chat_message` for each turn.
- **State:** `st.session_state` holds `df`, `schema_info`, `messages` (each with question, answer, result, result_type, code, error). Reloading the uploaded file resets the chat; cache the compiled graph with `st.cache_resource`.
- **Rendering by `result_type`:** `dataframe` → `st.dataframe`; `plotly` → `st.plotly_chart(use_container_width=True)`; `value` → `st.metric`; `text` → `st.write`. Past messages are re-rendered from `session_state`, not recomputed.
- **Code transparency:** a "Show generated code" expander under each answer (and the plan, plus retry count if > 0).
- **Failure state:** if retries are exhausted, show the last error in `st.error` with the final code in the expander, instead of a blank answer.
- **While running:** `st.spinner("Thinking…")`; handle the missing-API-key and rate-limit cases with clear messages.

**Check:** `streamlit run app.py`, upload `sales.csv`, and run all 8 sample questions in the browser. Then test the unhappy paths: non-CSV upload, empty CSV, a question about a column that doesn't exist, and a follow-up ("now only 2024") that depends on the previous answer. Confirm the layout at normal and narrow widths.

1. **`walkthrough.py`** — runnable script: load CSV → print the schema prompt → `ask()` for 3–4 sample questions → print the plan/code/results (save Plotly figures as HTML/PNG to an `outputs/` folder). Write this first; it is the source for the notebook.
2. **`walkthrough.ipynb`** — the same flow as markdown + code cells, built with `nbformat` from the script's sections, then executed (`jupyter nbconvert --execute --inplace`) so outputs are embedded. Needs the API key, so run it once and commit the executed version.
3. **`generate_report.py`** — `fpdf2` script producing `Project_Report.pdf`: overview, architecture and graph flowchart (draw it with `fpdf2` shapes, or render a Mermaid/graphviz image if available), the node descriptions, sample outputs with screenshots/PNG charts from the live run, a self-correction example showing a real traceback and the fix, limitations (sandbox, rate limits), and learnings.
4. **`Project_Report.pdf`** — output of the script. Open it and check pages visually.

**Check:** the script runs end-to-end from a clean venv; the notebook executes with no errors; the PDF opens and has no cut-off text or missing images.

## Risks

- **LLM output drift:** code with fences, prose, imports, or `print()`. Mitigated by the fence-stripper, the AST check feeding errors back into `fix`, and the explicit prompt rules.
- **Wrong-but-successful answers:** code runs without error but answers the wrong question; the retry loop can't catch this. The code expander and the plan display are the mitigation; note it in the README and report.
- **Free-tier limits or model changes:** handled by backoff and a configurable model name.
- **Plotly `heatmap` and `pie` need an aggregated frame:** include one-line hints in the code prompt (e.g. "for heatmaps use `px.density_heatmap` or pivot first") if the live check shows failures.
